# 续：解算时机从「打完」挪到「叫牌结束」

用户追问：「不能在对局进行中解算，然后再在对局结束后播报吗」。答案是可以，而且本来就该这样。

## 改法

- `beginDoubleDummy()` 挂在 `concludeAuction()` 的 `phase = Phase.PLAY` 之后。
  **只有这一刻**「将牌 + 首攻人 + 庄家方位 + 所需墩数」才全部确定；放 `beginAuction()` 将牌还是未知。
  牌越早开算越好 —— 整副牌 13 墩的打牌时间就是搜索预算，之前是让全桌盯着牌墩干等 1~25 秒。
- `collectDoubleDummy()` 在 `announceResult()` 末调用：`isDone()` → 同步播；没跑完 → `thenAccept` 等落地，不阻塞。
- `DoubleDummyAnswer(tricks, capped)` 让 future 带回：`lastWasCapped()` 是 static，回调里再读会被下一副覆盖。
- 回调只读捕获值（合同/庄家/所需/实得），不碰活字段。

## 一个结论：**不要加 token 去掐「晚回来的那副」**

先加了 `doubleDummyToken`，晚回来的答案发现牌桌已换副就咽掉。实测它在线上**永远等于 1**：
`CardTableBlock` 在 `game.isGameOver()` 后走 `TableScreenPayload → CardTableBlockEntity.startGame() → type.create(...)`，
即**每副牌都是新的 `BridgeGame` 实例**（`startGame()` 只在实例刚建好时被调一次）。
晚回来的 future 持有自己那份捕获值，`players` 又是同一批实体，所以**发出来才对**。删掉了。

## 双明手解算器性能优化（需求「你再优化一下代码，提高性能」）

只动 `BridgeDoubleDummy` 与 `.scratch/dd`，玩法/文案/选项布局不变；**每步都用"节点数是否逐位相同"作安全网**。

- **`TABLE_BITS` 21 → 24（32MB → 256MB）是唯一的大头**：`One` 最坏局面 20197ms/89M 节点 → 3891ms/20M 节点
  （5.2 倍）；`Hard` 20 局面最坏 21090 → 8944ms、总耗时 169616 → 74764ms（2.3 倍）。尺度：2^21=14869ms，
  2^22=8584，2^23=7613，**2^24=3891（拐点）**，2^25=3866，2^27=4684。往下缩会一路缩到破 a+b=13（2^19 撞上限且答案变小）。
  "表小"不只是探针慢，是**每次冲突白扔一整棵子树**。表是 `static final`，只在第一次解算随类初始化分配。
- 等价牌折叠的"全场 pattern"改增量维护（`PATTERN`/`PATTERN_N` + `pushPattern`/`seedPattern`）：
  20251 → 17044ms，节点数逐位相同。**下标必须用全局位号 `(1L<<card)-1`，不是 `card%13`**（写错会塌到 1.2M 节点、答案变小）。
- 置换表两并行数组 → 一个交错数组 `TABLE[]`（`[key, meta]`）：17044 → 14723ms。
- 量掉两个"看着有用"的（节点数逐位相同所以删得放心）：`WIN_KEY` 每着法增量维护 → 改回 `keyOf` 里每节点现算
  `bitCount`（14869 → 14676ms）；TT key 从 `lookup`/`store` 各建一次 → 每节点建一次传参。

**结论：这个解算器上"缓存/内存"比"搜索技巧"值钱得多**（killer/history 以前也量掉过）。改前先量节点数，节点数不变才知道没改变行为。

复核：`Validate` 3 副×5 将牌×4 首攻 = 60 项 `bad=0`、零和全绿；`BRIDGE_DEBUG_SCREEN=1 runClient`
连打 **8/8 副、8 条双明手播报**（1 条来自 `bridge-double-dummy` 线程＝异步路径，7 条同步），无异常、无 OOM（客户端堆约 2.7GB，256MB 表没问题）。

## 崩溃排查：deploy 原地覆盖 jar 把正在启动的游戏写坏（反馈「直接崩溃了」）

- 崩溃报告 `crash-2026-10-08_22.07.36-client.txt`：头部是 bridge 入口点
  `Could not execute entrypoint stage 'main' ... provided by 'bridge' at 'dev.bridge.BridgeMod'`，
  但 `Caused by` 是 `java.util.zip.ZipException: ZipFile invalid LOC header (bad signature)`，
  报的类是 `dev.myavalon.client.CardSlotAccess` —— **bridge 背锅，真正坏的是 MyAvalon 的 jar**。
- 定位手法（可复用）：① `unzip -t *.jar` 扫 mods 全目录（全 BAD 一眼分明）；② 比对 `mods/*.jar` 的
  **mtime 与崩溃时间** —— MyAvalon jar mtime 22:07、游戏 22:07:22 启动、22:07:36 崩，完全压在窗口上。
  注意 `unzip -t` 在部署完成后必然 OK，"现在测没事"能否掉不了这个诊断。
- 机理：`tasks.register('deploy', Copy)` 会把目标**截断再写**（同 inode 原地重写）；`ZipFile` 打开时缓存
  中心目录、之后按缓存偏移读条目 → 文件被重写后偏移全失效 → 之后每次读该类都报 invalid LOC header。
  所以**边部署边启动（或游戏在跑时部署）必炸**，且延迟到启动十几秒后才炸（读到那个类时）。
- 修法：拷到同目录 `xxx.jar.staged`，再 `Files.move(REPLACE_EXISTING, ATOMIC_MOVE)`。`.staged` 不会被
  loader 当 mod 扫到。**charta-bridge 和 MyAvalon 两边都改了 deploy**，都实测通过（部署后 md5 与
  build/libs 一致、无残留 .staged）。恢复动作：已重新部署 bridge 与 MyAvalon，jar 全部 `unzip -t` 通过。
- 提交 `a81c057`（只动 build.gradle 的 deploy + 文档，mod 代码零改动）；坑 90 已写进 CHARTA-SETUP.md。
