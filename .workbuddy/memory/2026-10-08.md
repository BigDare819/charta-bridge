## 做了什么

1. **功能**（前一会话已写大半，本次收尾+验证）
   - `BridgeGame` 第 5 个 `GameOption.Bool DOUBLE_DUMMY`（默认关，**必须加在选项列表末尾**，选项是按位置灌字节的）。
   - `rememberDeal()` 在 `beginAuction()`（刚发完牌）把四家手牌快照成 `long[4]`；打完后手牌是空的，只能快照。
   - `startDoubleDummy()`：单线程 daemon 线程池解算（`BridgeDoubleDummy` 全部状态是 static，含 32MB 置换表，只能串行），
     future 回调里 `server.execute(...)` 回主线程 `table(...)` 播报。**不能用 tick() 轮询**（`isGameOver` 一置真，
     下一 tick 就把 game 置 null）。客户端镜像 `findServer()==null` 直接 return。
   - lang 双语 + 两个说明页 + README 同步。版本 1.1.1 → 1.1.2。

2. **解算器修复（本次的核心）**
   - `collapse()` 的等价牌判据重写：`live = 四家手牌 ∪ {当前赢墩那张牌}`，保留每类**最高**张。
     两个坑：① 只看自己手里相邻 → 漏折；② 只看自己手里"下一张" → **过折**，答案直接变小（t2L2 10→7）。
     赢墩那张已离手、不在 hand0..3，但必须算 live。与 DDS( Haglund & Hein ) / Ginsberg partition search 一致。
   - 走子顺序：**killer + history 表是 6~8 倍回退**，只留"TT 命中着法提前"（中性）。最终删掉 killer/history。
   - `NODE_CAP` 40M → 150M。破上限返回的是界，`a+b==13` 立刻不成立 → 是**错**不是"不精确"。
   - 4 副 × 5 花色 × 4 家首攻实测最坏单局面 **89M 节点 / 21s**（原 104M / 28s）。

3. **验证**：`.scratch/dd` 的 `Validate`（3 副 × 5 × 4 × 双方，断 `a+b==13` 且未破上限）60/60 全绿；
   手验 20 局 + 3637 万窗口断言仍绿；`gradlew build` 成功（仅 3 条既有 `@Accessor` 警告）。

# 续：解算时机从「打完」挪到「叫牌结束」

用户追问：「不能在对局进行中解算，然后再在对局结束后播报吗」。答案是可以，而且本来就该这样。

## 改法

- `beginDoubleDummy()` 挂在 `concludeAuction()` 的 `phase = Phase.PLAY` 之后。
  **只有这一刻**「将牌 + 首攻人 + 庄家方位 + 所需墩数」才全部确定；放 `beginAuction()` 将牌还是未知。
  牌越早开算越好 —— 整副牌 13 墩的打牌时间就是搜索预算，之前是让全桌盯着牌墩干等 1~25 秒。
- `collectDoubleDummy()` 在 `announceResult()` 末调用：`isDone()` → 同步播；没跑完 → `thenAccept` 等落地，不阻塞。
- `DoubleDummyAnswer(tricks, capped)` 让 future 带回：`lastWasCapped()` 是 static，回调里再读会被下一副覆盖。
- 回调只读捕获值（合同/庄家/所需/实得），不碰活字段。

## 一个结论：**不要加 token 去掐「晚回来的那副」**

先加了 `doubleDummyToken`，晚回来的答案发现牌桌已换副就咽掉。实测它在线上**永远等于 1**：
`CardTableBlock` 在 `game.isGameOver()` 后走 `TableScreenPayload → CardTableBlockEntity.startGame() → type.create(...)`，
即**每副牌都是新的 `BridgeGame` 实例**（`startGame()` 只在实例刚建好时被调一次）。
晚回来的 future 持有自己那份捕获值，`players` 又是同一批实体，所以**发出来才对**。删掉了。
